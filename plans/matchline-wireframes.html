match|line — wireframes, every screen at three widths

One product, one source per screen, drawn three times. Each frame renders the same markup inside a desktop (1280×800), tablet (834×1112) and phone (390×844) canvas; the layout re-flows per width with container queries, so a tablet or phone frame shows the responsive proposal, not a shrunken desktop. Every frame carries a stable anchor of the form #fx-<screen>-<state>-<width> (desk / tab / ph). Captions under the desktop frame describe the state; captions under the tablet and phone frames describe only what changes at that width.

Sources, in the order they win: the PRD's v0.2 "job-search dossier" revision (October 2026; where it conflicts with the V1 interface section, the revision wins), what is shipped in src/routes/** (Sign in, Onboarding, Unit Review, Role Detail, Application Editor, New Role, Pipeline with stage moves), BRAND.md, docs/design/ui-guidance.md (Attio-like: monochrome, one accent, dense, inline over modal, keyboard-first, fail visibly) and specs/matchline.md. All sample data — companies, people, résumé lines, figures — is invented. Nothing is taken from any real search.

How to read a frame.
· Chips above a frame name the width and whether the frame is shipped (matches the built route), PRD v0.2 (proposed, not yet built) or a state (empty / loading / error / validation variant of a screen).
· Dashed outline like this inside a frame marks one element that the PRD adds and nothing has built yet — the rest of that frame is shipped behaviour.
· Numbered badges 1 point at the annotation with that number in the legend under the screen. The legend is written once per screen and applies to all three widths.
· Keyboard: a-style keys show the shortcut the control also answers to; every mouse action in these frames is keyboard-reachable (ui-guidance rule 5).
· Zoom (control below) scales the desktop and tablet canvases; the phone canvas is 1:1 by default. Nothing inside re-flows when you zoom — only the real width does that.

Known deltas — where this document is deliberately ahead of the app. Every one is tracked so a reviewer can tell a decision from a mistake.
· Navigation. The shipped shell (src/App.tsx) has a top nav of Onboarding · Unit Review · + New Role · Application Editor · Pipeline. These frames draw the v0.2 shape — Pipeline · Evidence (Units, Canonical résumé, Claim rules) · Scan · + New Role, plus ⌘K — and, on the phone, a bottom tab bar. Both are proposals (dashed).
· Pipeline stages. The board ships with seven columns (Saved, Drafting, Applied, Interviewing, Offer, Rejected, Withdrawn — src/routes/Pipeline/PipelineView.tsx). The PRD's dossier objects propose a nine-stage vocabulary (saved, researching, referral_requested, applied, screening, interviewing, leveling, offer, closed with a reason). The frames keep the shipped seven and name the proposal here rather than drawing an unbuilt board.
· Role detail tabs. Shipped: Requirements · Matches · Applications. Drawn: Fit brief (default) · Requirements & matches · Package · Process · Correspondence, per PRD § Interface additions. The Requirements & matches tab keeps the shipped Matches behaviour (gaps surfaced inline, approve / reject shortcuts, "Computing matches…", re-run).
· Tasks sidebar (#34) and the card's next-action chip (#512) are not merged; the frames draw #34's three sections (Due today / Upcoming / Follow-ups) and the chip as proposed.
· Onboarding ships as a single paste-résumé textarea; the three-pane import with four sources is ui-guidance's stated V1 shape, drawn here with LinkedIn, long-form and artifact upload marked as not built (#28, #29, #87).
· Weekly scan, canonical résumé editor, claim rules, Process and Correspondence have no shipped surface at all; every frame of those is PRD v0.2.
